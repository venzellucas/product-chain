# Problem statement format → `01-problem.md`

A good problem statement is specific, falsifiable, and about a *user and a pain* — not a solution.
Method cues: Teresa Torres (problem before solution), Amazon Working Backwards.

```markdown
# Problem: <short title>

## Problem statement
One or two sentences: WHO has WHAT pain, WHEN/where, and why current options fall short.
State it as a problem, not a feature.

## Target user (ICP)
The specific person/segment. Narrow beats broad. Note how reachable they are.

## Job to be done
The progress the user is trying to make ("when ___, I want to ___, so I can ___").

## Riskiest assumptions (most dangerous first)
1. <assumption> — why it's risky, and how it could be tested cheaply
2. ...
(The single assumption that, if false, kills the idea goes first.)

## Success metric
The one number that would prove this problem is worth solving (and a rough threshold).

## Research angles
Concrete things Phase 2 should chase — name suspected incumbents/alternatives and the search
queries / questions that would reveal demand and the competitive gap. One bullet per angle.
```

Keep it to a page. If the user or problem is unknown, say so explicitly — that's a Gate G1 signal.
